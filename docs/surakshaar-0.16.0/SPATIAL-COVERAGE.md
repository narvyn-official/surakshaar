# Detailed spatial learning · 0.16.0-rc.1

This upgrade reuses SurakshaAR’s native equipment, procedural states, first-aid teaching apparatus and licensed anatomy. Android and web now share an explicit spatial plan for every current curriculum step. There is no course-level generic-model fallback.

## Coverage and interaction

- **20 current scenarios / 94 steps:** each has a named equipment, route, teaching-apparatus or anatomy scene. Android opens the step inspector from the lesson; web embeds it beside the question. Required anatomy observations still need their own explicit action.
- **5 industrial procedures / 55 ordered steps:** restored to the web from the native procedure catalog, with choices, feedback, saved local checkpoints, resume, reset and changing specimen geometry. Keyboard/button actions and 3D action markers use the same replay logic. Invalid or skipped events cannot advance the sequence.
- **Original Android practice retained:** component identification, native procedure views, fire/gas room missions, equipment gestures, eight adult first-aid bay situations and the 117-structure anatomy explorer. The web rehearsal does not reproduce every native room gesture or live teaching animation.
- **AR availability:** Android uses the existing ARCore scene owners with explicit permission and placement. Web uses a supported browser’s WebXR hit test to place a half-scale illustration. Both retain ordinary 3D views. Web placement is in the session’s local reference space, not a persistent room anchor or hazard detector.
- **Inspection is separate from assessment:** opening a view, rotating, zooming, placing AR or inspecting a detail does not create an answer, prove physical competence, verify identity or issue a certificate.

## Asset and runtime architecture

`content/spatial/catalog.json` is the step and detail map. `WorldEquipment`, `EquipmentDetailGeometry`, `FirstAidTeachingProps`, `FirstAidEquipment` and `AnatomyClothing` own native geometry. The native export contract emits CPU mesh data; `scripts/build-spatial-assets.py` writes indexed, self-contained GLBs for Three.js. The procedural catalog is exported from native code rather than manually copied.

The manifest contains **29 optional GLBs**, **10,524,092 bytes total**, and **368,056 triangles across all variants**. These are aggregate asset totals, not a single rendered scene. The browser loads the selected view, limits pixel ratio, renders static scenes on demand, disposes resources when leaving, and preserves written learning when graphics fail. External-buffer/texture GLBs are rejected before parsing. Native mesh construction uses primitive float storage and anatomy decompression streams into bounded final arrays to reduce transition-time allocations. Live anatomy scenes share verified read-only geometry through a weak cache; learner answers and camera/render state remain per scene.

Rebuild: run the Android `SpatialAssetContractTest` with an absolute `SURAKSHA_EXPORT_PATH`, then run `python3 scripts/build-spatial-assets.py`. Anatomy GLBs remain generated by `scripts/build-web-anatomy.py`; regenerate spatial assets afterwards to add the protected external-skin metadata. Keep all asset notices alongside distribution.

## Remaining acceptance work

Physical Android/browser AR tracking, lighting changes, long-session thermal behavior and device-specific camera recovery still require supported real phones. New detail labels and the new procedure web UI are primarily English; complete Hindi review and assistive-technology testing remain pending. All 20 current scenarios remain draft and non-certifiable; future chapters listed in the learning catalog are not represented as completed modules. No statutory certification, guaranteed injury prevention or emergency diagnosis is claimed.

## Restored procedure sequences

### Fire response sequence · 16 steps

1. `fire-alarm` — A small simulated fire has appeared.
2. `fire-authorisation` — The scene assigns a trained, authorised responder with a clear retreat path.
3. `fire-label` — The training extinguisher has not yet been checked.
4. `fire-service` — Inspect the virtual inspection label: service status is unconfirmed.
5. `fire-hose` — The replacement has a visibly damaged hose. Inspect before selecting it.
6. `fire-gauge` — A new unit has a model-specific status indicator.
7. `fire-pin` — The role, retreat path and extinguisher checks are complete in this scene.
8. `fire-aim` — The pin is removed. The nozzle is not yet aimed.
9. `fire-squeeze` — The nozzle is aimed at the base.
10. `fire-sweep-left` — Simulated discharge is now active.
11. `fire-sweep-right` — The nozzle has reached the left side of the base.
12. `fire-sweep-return` — The nozzle has reached the right side of the base.
13. `fire-withdraw` — Conditions now worsen in the simulation.
14. `fire-exit` — You have withdrawn. The marked left exit is clear; the other route is blocked.
15. `fire-assembly` — You are outside at the designated assembly point.
16. `fire-handover` — At assembly, the responsible person asks what happened.

### Confined-space entry boundary · 13 steps

1. `gas-boundary` — An unverified confined space is ahead.
2. `gas-instrument` — The SIM instrument shows a low-battery warning.
3. `gas-record` — The instrument check record is missing.
4. `gas-permit` — The boundary is secured. Entry controls have not yet been reviewed.
5. `gas-isolation` — The permit calls for equipment-specific isolation.
6. `gas-atmosphere` — Isolation is recorded in the scenario. Atmospheric assessment remains unconfirmed.
7. `gas-ppe` — The scenario identifies hazards and the worker's role.
8. `gas-attendant` — The team is assembled. No attendant position is assigned.
9. `gas-communication` — The attendant is outside. Team communication has not yet been checked.
10. `gas-contact-loss` — Radio contact is lost during the outside-role rehearsal.
11. `gas-handover` — A replacement attendant arrives.
12. `gas-rescue` — The rescue contact now fails to respond in this scenario.
13. `gas-refuse-entry` — Rescue readiness is missing, despite the earlier checks.

### Isolation and handover mission · 10 steps

1. `mach-role` — A conveyor has stopped. A colleague asks you to clear a jam.
2. `mach-sources` — Inspect the illustrated electrical drive and raised load.
3. `mach-notify` — People nearby may operate the machine.
4. `mach-isolate` — The scene offers a stop button and an identified isolating device.
5. `mach-lock` — The authorised worker has a personal lock and identification tag.
6. `mach-stored` — The raised load remains an unresolved stored-energy hazard.
7. `mach-verify` — A colleague claims isolation is complete without a verification record.
8. `mach-shift` — A shift change occurs while the task remains open.
9. `mach-restart` — The simulated maintenance is finished; a guard is still missing.
10. `mach-report` — Complete the handover with remaining restrictions.

### Inspect, select and replace PPE · 8 steps

1. `ppe-hazard` — The scenario describes flying particles and a designated outside role.
2. `ppe-label` — Two similar items have different approved uses.
3. `ppe-crack` — The helmet illustration shows a crack in the shell.
4. `ppe-eye` — The eye protection is damaged and blocks the view.
5. `ppe-glove` — The supplied glove has a visible tear.
6. `ppe-compatible` — The selected items must work together.
7. `ppe-change` — The task changes to an unassessed atmosphere.
8. `ppe-store` — The practice ends with equipment inspection and reporting.

### Incident, evacuation and accountability · 8 steps

1. `em-scene` — A simulated incident is ahead; scene safety is unknown.
2. `em-alert` — The emergency contact needs an initial report.
3. `em-route` — The first marked route is now obstructed.
4. `em-support` — A colleague needs assistance beyond your training.
5. `em-assembly` — The group reaches the simulated assembly point.
6. `em-missing` — The roster lists six people; only five are accounted for.
7. `em-rumour` — Someone says it is safe to return without an authorised message.
8. `em-log` — The coordinator asks for a factual incident handover.
