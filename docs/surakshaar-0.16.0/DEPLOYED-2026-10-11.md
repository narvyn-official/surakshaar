## Recovery and limits

Keep the previous application at `/opt/surakshaar/releases/20261010-accounts-v1` and the protected recovery set at `/var/backups/surakshaar/20261011-spatial-0.16.0`. It contains the stopped-write pre-cutover database, matching configuration and original systemd/nginx files. Scheduled backups retain 14 days on the same server; off-server recovery and alert delivery remain unconfigured.

For application rollback, stop only SurakshaAR, take a fresh verified backup, restore `service.before`, point `current` to the saved previous release, reload systemd and start the service. These migrations add tables and leave the old schema intact; retain the new tables and current data. Stop the new maintenance timer when reverting to the older release, which lacks its cleanup script; the existing backup service remains compatible. Verify login and record access. Do not restore the pre-cutover database over newer learner records. A database recovery is a separate deliberate operation requiring preservation of the current DB/WAL and isolated validation first.
